File: frontend-patient/src/pages/ConversationPage.tsx  (lines 85-116)

The microphone is NOT a separate component — it is inline in ConversationPage.

The implementation uses the browser's MediaRecorder Web API:

  const startRecording = async () => {
    // Toggle recording on/off (same button)
    if (isRecording && recorderRef.current) {
      recorderRef.current.stop();
      return;
    }
    try {
      // 1. Request microphone access
      const mediaStream = await navigator.mediaDevices.getUserMedia({ audio: true });

      // 2. Create MediaRecorder with audio/webm MIME type
      const recorder = new MediaRecorder(mediaStream, { mimeType: 'audio/webm' });

      chunks.current = [];
      recorder.ondataavailable = e => {
        if (e.data.size) chunks.current.push(e.data);
      };

      // 3. On stop: assemble blob, send to backend for transcription
      recorder.onstop = async () => {
        mediaStream.getTracks().forEach(t => t.stop());  // release mic
        setIsRecording(false);
        setLoading(true);
        try {
          const audioBlob = new Blob(chunks.current, { type: 'audio/webm' });
          const result = await voiceApi.transcribe(sessionId, audioBlob as File, lang);
          const transcript = result?.transcript || result?.text || result?.transcription || '';
          setInput(transcript);  // Pre-fill textarea with transcript
        } catch {
          setInput('');          // Silently fail; user types manually
        } finally {
          setLoading(false);
        }
      };

      recorderRef.current = recorder;
      recorder.start(1000);     // Collect chunks every 1000ms
      setIsRecording(true);
    } catch (e) {
      console.error('Mic access denied', e);
    }
  };

State variables used:
  const [isRecording, setIsRecording] = useState(false);

  const recorderRef = useRef<MediaRecorder | null>(null);

6. REQUEST / RESPONSE SCHEMAS
================================================================================

STT Request (frontend -> backend):
  Method: POST /api/v1/cases/{session_id}/voice/transcribe
  Content-Type: multipart/form-data
  Fields:
    audio  : File (audio/webm blob from MediaRecorder)
    (implicit query param) language_code: string  e.g. "hi", "ta", "en"

STT Response (backend -> frontend):
  Python dict / JSON:
  {
    "transcript": string,       // recognized text
    "confidence": float,         // 0.0 - 1.0
    "language": string,          // echo of requested language_code
    "provider": string           // "mock" | "sarvam"
  }

TTS Request (frontend -> backend):
  Method: POST /api/v1/cases/{session_id}/conversation/speak
  Content-Type: application/json
  Body:
  {
    "text": string,             // question text to speak
    "language_code": string     // e.g. "hi", "ta"
  }

TTS Response (backend -> frontend):
  {
    "audio_base64": string,     // base64-encoded audio (Sarvam), or "mock" string (mock)
    "duration_seconds": float,  // e.g. 2.0
    "provider": string,          // "mock" | "sarvam"
    "status": string            // "success" | "unavailable" (Sarvam only; mock always "success")
  }

Note: schema file backend/app/schemas/tts.py defines TTSRequest/TTSResponse
types (text, language_code, voice, speed fields), but the endpoint does not
use Pydantic validation — it receives raw text + language_code from JSON body.

8. WHAT HAPPENS WHEN THE PATIENT SPEAKS AN ANSWER
================================================================================
Step-by-step through ConversationPage.tsx lines 85-116:

Step 1 — User taps microphone button:
  startRecording() fires.
  navigator.mediaDevices.getUserMedia({ audio: true }) requests mic permission.
  If denied: catches error, logs "Mic access denied", does nothing else.
  If granted: creates MediaRecorder(mediaStream, mimeType: 'audio/webm').
  recorder.start(1000) — begins collecting audio chunks every 1 second.
  isRecording = true -> mic button turns red + pulse animation.

Step 2 — User speaks (audio is collected):
  recorder.ondataavailable fires every 1000ms.
  Each audio chunk is appended to chunks.current (Blob[] array).

Step 3 — User taps microphone button again (stop):
  recorder.stop() is called.
  recorder.onstop fires:

  a) mediaStream.getTracks().forEach(t => t.stop()) — releases microphone hardware.

  b) audioBlob = new Blob(chunks.current, { type: 'audio/webm' }) — assembles full recording.

  c) setLoading(true) — shows loading spinner.

  d) voiceApi.transcribe(sessionId, audioBlob, lang)  [lang from sessionStorage]

     Backend:
       POST /cases/{sessionId}/voice/transcribe?language_code={lang}
       -> Mock returns: { transcript: "Mock transcription for testing purposes", ... }
       -> Sarvam returns: { transcript: "...actual recognized text...", confidence: 0.x, ... }

  e) Frontend extracts transcript:
       const transcript = result?.transcript || result?.text || result?.transcription || '';

  f) setInput(transcript) — transcript is PRE-FILLED into the textarea.
     The patient can edit the text before submitting.

  g) setLoading(false) — hides spinner.

Step 4 — Patient submits (typed or edited):
  handleSubmitAnswer() fires when "Next" button is clicked.
  Calls conversationApi.respond(sessionId, { answer_text: input, input_mode: 'touch' })
  Note: input_mode is ALWAYS 'touch' even for voice answers (see line 64).
  The transcript is treated as typed text.

CRITICAL OBSERVATION: The microphone button record -> stop -> transcribe flow is
fully client-side. The browser collects raw audio via MediaRecorder, sends it to
the backend, and gets back a transcript. The patient always has a chance to edit
the transcript in the textarea before submitting.

9. WHETHER RECOGNIZED TEXT IS STORED IN THE PATIENT SESSION
================================================================================
NO. The transcript from voiceApi.transcribe is used only to pre-fill the textarea
(setInput). It is NOT stored in sessionStorage and is NOT sent to the backend as
a 'voice' input_mode.

In handleSubmitAnswer (line 62-65):
  conversationApi.respond(sessionId, {
    answer_text: input,          // whatever is in textarea (voice transcript or typed text)
    input_mode: 'touch',         // HARDCODED to 'touch' regardless of how text was entered
  });

The frontend has an InputMode type: 'voice' | 'touch' | 'voice_edited' | 'ocr'
but the voice input path never sends 'voice' or 'voice_edited' — it sends 'touch'.

The backend session (PatientSession, ClinicalCase) stores clinical_history (facts)
but the raw transcript is not stored separately per answer. The answer_text is
processed by conversationApi.respond which sends it to the backend, but the
backend's conversation engine processes it as text — the original input_mode flag
would be 'touch' even for a voice answer.

The transcript itself is not stored anywhere in sessionStorage or localStorage.
It lives only in React component state (input string) until submission.

10. WHETHER THE SELECTED LANGUAGE CONTROLS STT AND TTS
================================================================================
YES — partially.

Language selection (LanguagePage.tsx line 63):
  sessionStorage.setItem('medikiosk_lang', selected);  // e.g. 'hi', 'ta', 'bn'

All subsequent voice calls read this value:

  const lang = sessionStorage.getItem('medikiosk_lang') || 'en';

STT call (ConversationPage.tsx line 101):
  const result = await voiceApi.transcribe(sessionId, audioBlob, lang);
  -> Backend receives: language_code = lang
  -> Sarvam: forwards language_code to Sarvam API
  -> Mock: ignores language_code, returns hardcoded English text

TTS call (ConversationPage.tsx line 31):
  await voiceApi.speak(sessionId, getQText(q), lang);
  -> Backend receives: { text, language_code: lang }
  -> Sarvam: forwards language_code to Sarvam Bulbul API
  -> Mock: ignores language_code

The frontend always sends the selected language code. Whether it has any effect
depends on the backend provider:
  Mock: no effect — always returns English mock data.
  Sarvam: language_code is forwarded to Sarvam API for real ASR/TTS.

The LanguagePage displays per-language ASR/TTS capability badges from the backend
(/languages endpoint), but these are informational only — they do not gate or
prevent voice calls. A user could select a language with no ASR badge and still
trigger a voice recording; the Sarvam API would receive an unsupported language_code.

CURRENT VOICE FLOW — QUESTION -> TTS -> MICROPHONE -> STT -> CONFIRM -> SUBMIT
================================================================================

Frontend (ConversationPage.tsx)                     Backend (clinical_history.py)
─────────────────────────────────                  ──────────────────────────────

1. QUESTION LOADED
   conversationApi.start() -> backend returns
   first_question { text: { en, hi }, section }

2. TTS (question read aloud)
   voiceApi.speak(sessionId, question_text, lang)  → POST /conversation/speak
   Backend: get_tts_provider().synthesize(text, lang_code)
   Response: { audio_base64, duration, status }
   FRONTEND DISCARDS audio_base64 — not played!
   Only UI animation: setIsSpeaking(true) for 1s

3. PATIENT TAPS MICROPHONE (startRecording)
   navigator.mediaDevices.getUserMedia({ audio: true })
   MediaRecorder.start(1000) — chunks collected every 1s

4. PATIENT TAPS MICROPHONE AGAIN (stop)
   MediaRecorder.stop()
   recorder.onstop fires:
     audioBlob = Blob(chunks, 'audio/webm')
     voiceApi.transcribe(sessionId, audioBlob, lang)
       → POST /voice/transcribe?language_code={lang}
       Backend: get_speech_provider().transcribe(audio_bytes, lang_code, mime)
         Mock:  returns { transcript: "Mock transcription for testing...", ... }
         Sarvam: returns { transcript: "actual patient words", confidence, ... }
     transcript = result.transcript
     setInput(transcript)  ← PRE-FILLS TEXTAREA

5. CONFIRMATION (implicit)
   Patient sees transcript pre-filled in textarea.
   Patient CAN edit the text before submitting.
   No explicit "confirm" button for voice — same Next button used for all input modes.

6. STRUCTURED ANSWER (submit)
   Patient taps "Next":
     conversationApi.respond(sessionId, {
       answer_text: input,      ← transcript (or edited text)
       input_mode: 'touch',     ← ALWAYS 'touch', even for voice!
     })
       → POST /cases/{sessionId}/conversation/respond
       Backend processes answer_text as free-form text.
       Extracts structured facts, returns next_question or is_complete.
     If is_complete: conversationApi.submit(sessionId)
       → POST /cases/{sessionId}/history/submit
       Navigate to /documents

IMPORTANT: input_mode is always 'touch' even for voice answers.
The input_mode type supports 'voice' and 'voice_edited' but these are never sent.
The frontend has no code path that sends 'voice' or 'voice_edited'.
